## 0. Цель и неизменяемые границы

Довести существующую HTML5 idle-RPG «Храбролап» до выпускаемого мобильного качества для публикации в Яндекс Играх:

- 2000 волн; 10 сюжетных глав по 200 волн; 200 различимых залов по 10 волн.
- 10 обычных видов монстров и 40 уникальных супербоссов через каждые 50 волн.
- Сюжет 40 печатей, поворот с Повелителем глубин, добрый финал и добровольный постгейм.
- Единый ламповый 2D-стиль; визуальное качество новых объектов соответствует уже принятому котёнку.
- Стабильный бой, рыбалка, торговец, магазин, броня, оружие, достижения и сохранения.
- **Сохранить утверждённые** котёнка, рыцаря-рыбака, серого торговца, позы атаки, хват меча, настоящие игровые фоны и сценарии сна, пока пользователь отдельно не разрешит правку.
- **Не создавать игру заново.** Все изменения — в `Elusivedamir/hrabrolap`.

Документы фиксируют **цель и стандарты**. Готовность каждого файла, модели, главы, механики и релиза устанавливается только тестами и отдельной художественной приёмкой.

## 3. P0 — безопасность текущей игры и база регрессий

**Цель:** не потерять то, что уже работает, и не повредить существующие сохранения или изображения.

1. Сохранить **конкретный Git SHA** текущего рабочего состояния, предыдущий тестовый ZIP и QA-артефакты.
2. Собрать список реально используемых рендерером canonical-кадров (`assets/canonical/`) и принятых моделей рыцаря, торговца, дома и экипировки; сверить `tests/locked-art-shas.json` и исторические QA-документы.
3. Снять базовые **реальные** скриншоты 320 / 360 / 390 / 412 CSS px: пристань, бой, магазин, инвентарь, ведро, задания, достижения, отдых, первый супербосс.
4. Зафиксировать текущие кривые урона, брони, скорости и золота в отчёте. Не менять числа без отдельного решения о балансе.
5. Проверить CI: автоматические `git push`/создание старого тега после теста, сборочные промежуточные файлы, правила сохранения доказательств. Разделить тестовую сборку и публикацию; автозамену принятой графики без утверждения запретить.

### P0.2. Сохранения
- Миграции старых версий вплоть до VERSION=6, включая старые 100- и 700-волновые прохождения.
- Не терять `gold`, `autoLevel`, купленные мечи/броню, зачарования, материалы, рыбу, все старые ID заданий/достижений и `megaBossWins`.
- Повторное открытие страницы, закрытие во время боя/отдыха/продажи, быстрое переключение режимов.
- **Android localhost / порт:** `http://127.0.0.1:8080` и `http://127.0.0.1:8090` имеют разные хранилища `localStorage`. Переход по новому порту не переносит сохранение: перед ним нужен отдельный экспорт/импорт либо возврат к прежнему адресу.
- При тестировании никогда не сбрасывать боевой личный прогресс пользователя без подтверждения; тестовые профили изолированы.

### P0.3. Тестовый переключатель торговца
- Обычная игра: штатный пятиминутный цикл.
- `?merchantTest=1`: первый визит через 15 секунд, затем короткое тестовое окно и следующий визит в 15-секундном цикле.
- Видимый тестовый обратный отсчёт, корректная продажа рыбы, возвращение из тестового режима к обычному без переноса ускоренного таймера в обычное сохранение.
- Таймер клёва **не выводить** на экран.

**P0 Done:** исходные спрайты и сохранения не повреждены, зелёные `npm test`, `qa:balance`, `qa:browser`, есть базовые скриншоты и проверенный откат/экспорт. CI больше не делает неожиданных публикаций арта.

## 9. P6 — финальная сцена, завершение и постгейм

**Волна 2000:**
1. Повелитель глубин побеждён; раскрывается, что он был Хранителем Искры.

4. Храбролап кладёт меч и засыпает дома.

**Техническое ТЗ:**

## 10. P7 — звук, оптимизация и контроль качества

### Звук и анимация
- Отдельные короткие SFX: меч, получение урона, монеты, рыба/ведро, прибытие торговца, получение достижения, появление босса.

- `prefers-reduced-motion` и пропуск катсцен; доступность управления не зависит от длинных эффектов.

### Мобильная производительность
- Испытать реальный Android в Chrome и встроенном браузере платформы; отдельно Chromium с ширинами 320/360/390/412/768 px и с короткой высотой.
- Измерить FPS/плавность, время первого отображения, общий размер ассетов, память на долгой сессии и при переходах между биомами. **Не назначать фальшивые результаты измерений**.
- Предзагрузка кадров активного боя, разгрузка неиспользуемых комнат/арт-паков, ограничение частиц и слоёв, проверка прозрачности.
- Проверка в нормальной сети и офлайн (локальная HTML5-сборка). Если шрифты внешние — честный фолбэк или поставка собственных лицензионно разрешённых WOFF2.

**P7 Done:** на реально проверенных Android-устройствах интерфейс управляем и не сбоит, а результаты производительности измерены и записаны.

## 11. P8 — релиз и подготовка Яндекс Игр

- Актуализировать версию, заголовок, описания, иконки, политику сохранений и режим без сети в соответствии с реальными правилами площадки **на момент публикации**.
- Сверить права на использованные визуальные и звуковые материалы.
- Устранить исторические ярлыки `v0.9.7` там, где они могут запутать игрока в новой сборке, **но не менять ID сохранений без миграции**.
- Подготовить артефакт `ZIP`, собранный **из конкретного протестированного SHA**; не выдавать предыдущий ZIP за последний релиз.
- Проверить запуск из архива на Android и платформенном тестовом стенде, отсутствие внешних обязательных зависимостей и корректность паузы/возобновления.
- Релиз и рекламные механики площадки — **только после отдельного согласования**. Не добавлять рекламу «по умолчанию».

**P8 Done:** воспроизводимый билд, SHA, QA-отчёт, сборка ZIP, лицензии/метаданные, поддерживаемые сохранения и явное разрешение пользователя на публикацию.

### Команды существующего проекта

```bash
npm ci --ignore-scripts
npm test

# В отдельной сессии / терминале:

# Во второй сессии с доступным установленным Chromium:

# Полный объединённый сценарий:
npm run qa
```

CI существует в `.github/workflows/qa.yml`, но **зелёная галочка CI не равна художественной приёмке**. Если Chromium/Android/платформа в данный момент недоступны, соответствующую проверку помечать `NOT RUN`, не заявлять PASS по косвенным данным.

### Симуляция баланса — правила интерпретации

- Стратегии должны быть воспроизводимыми (фиксированные seed, известная политика покупок, лимит времени, лог прохождений/поражений).
- Не делать вывод, что игрок пройдёт за N реальных минут, по виртуальному времени ускоренного прогона.
- **Вампиризм 5% на успешный удар**, ограниченное исцеление; на бесплотных существах нет лечения. Проверка статистического разброса по нескольким seeds.
- Скорость автоатаки плавно растёт по уровням; ручной бой не должен обходить лимит частоты.
- Доход золота сравнивать с ценами оружия, брони, удочки и дома, включая повторный фарм боссов; не полагаться только на общий итог суммы.
- Точечные изменения числового баланса — отдельное согласование после данных симуляции.

## 13. Обязательные ворота качества (release gates)

1. **G0 — спецификация:** принято ТЗ изменения, границы неизменяемых ассетов известны.
2. **G1 — исходники и SHA:** все затронутые файлы известны, старые данные защищены.
3. **G2 — функциональность:** unit, контрольные проверки и `qa:balance` проходят; нет новых JS-ошибок.
4. **G3 — реальный рендер:** Chromium открывает мобильную сцену и проверяет фактические изображения; снимки приложены.
5. **G4 — художественная приёмка:** пользователь видит реальные кадры/анимации **именно того файла, который будет включён в игру**, утверждает или возвращает на исправление.
6. **G5 — сохранения:** reload, старые версии, трофеи, покупки, награды и long-run работают.
7. **G6 — интеграция:** интеграционный коммит в `main` после зелёных тестов и нужной приёмки, повторный CI уже на `main`.
8. **G7 — сборка:** скачать/собрать ZIP **из одобренного коммита**, повторно проверить игру из архива, сохранить доказательства. Не объявлять релиз готовым до успешного G0–G7.

### Статусы задач
`proposed` → `spec-approved` → `in-progress` → `technical-tested` → `visual-approved` → `merged` → `release-tested`.

Не путать `technical-tested` и `visual-approved`. Пример: 480 процедурных SVG могут пройти структурный тест, но быть не приняты как нарисованная вручную художественная анимация.

### Процесс GitHub
- Новая задача → короткий issue/чек-лист → **отдельная ветка** `feature/<topic>` или `fix/<topic>`; исходный `main` не разрушать.
- Маленькие PR по одной задаче, с кратким перечнем затронутых канонических файлов и рискованных решений.
- Коммит/PR с ссылками на QA-отчёт и реальные скриншоты. Merge только после нужного одобрения; повторить CI в `main`.
- При провале теста откатить **только** конкретное изменение/PR, не сбрасывая личные сохранения пользователя.
- Автоматически создаваемые GitHub Actions теги и коммиты изображений следует сначала сделать предсказуемыми, чтобы CI не менял художественные файлы незаметно.

## 14. Паспорта работ и отчёт об итерации

**Для каждой конкретной задачи заводить запись:**

```text
ID: ART-BOSS-050 / MAP-R005 / UI-INVENTORY / STORY-2000 / CORE-SAVE
Статус: proposed | spec-approved | in-progress | technical-tested | visual-approved | merged
Задача: одно измеримое изменение
Ссылки: GitHub issue, PR, commit SHA, путь ассета
Что запрещено менять: перечисление canonical-файлов и UI-позиций
Проверки: npm test / balance / browser / Android
Скриншоты: реальные размеры экрана, прежде/после
Принято пользователем: да/нет (когда нужно)
Релизный ZIP: путь + SHA исходного коммита (только после сборки)
Незакрытые дефекты: ...
```

### Структура итогового отчёта

- Что изменено — только факты, с ссылкой на SHA.
- Что осталось нетронутым — защита канона.
- Какие проверки реально запускались — `PASS / FAIL / NOT RUN`.
- Визуальные примеры — **реальные** кадры из игры, не концепт-картинки.
- Как запустить на Android и где открывать — с учётом порта и `localStorage`.
- Что требует решения пользователя — конкретные модели, цвета, сюжетные сцены.
- Следующая маленькая задача — не «готова вся игра», если ещё не приняты арт-паки.
